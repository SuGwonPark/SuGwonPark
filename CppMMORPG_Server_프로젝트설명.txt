==============================================================
 C++ MMORPG 서버 개인 프로젝트
==============================================================

기간      : 2026-09 ~ 진행 중
인원      : 1인 개발 (서버 전체 설계 및 구현)
사용 언어 : C++
네트워크  : Boost.Asio 기반 TCP 비동기 I/O
DB        : MySQL (X DevAPI)
개발 환경 : Visual Studio, vcpkg, Git
기타      : libsodium(비밀번호 해시), magic_enum


--------------------------------------------------------------
1. 프로젝트 소개
--------------------------------------------------------------
7년간 Node.js로 라이브 서비스 서버를 개발·운영하면서 이벤트 루프
기반 구조의 한계를 체감했고, 스레드 모델과 메모리를 직접 설계하는
실시간 서버를 만들기 위해 C++ MMORPG 서버를 처음부터 개발하고
있습니다.

로그인부터 캐릭터 생성·선택, 존 입장, 이동, 전투, 스킬, 보상,
필드 드롭, 인벤토리, 존 이동까지 MMORPG 서버의 기본 흐름을
직접 구현했습니다.


--------------------------------------------------------------
2. 서버 구조
--------------------------------------------------------------

  [Client] ──TCP──▶ [Gateway Server] ──TCP──▶ [Zone Server]
                        │                        │
                        │ 로그인 / 캐릭터         │ 게임 로직
                        │ 세션 관리               │ (존 × 채널)
                        ▼                        ▼
                    [Account DB]             [Game DB]

  - Gateway Server
    클라이언트 접속, 로그인, 캐릭터 목록·생성·선택, 세션 관리.
    게임 패킷은 해당 Zone으로 전달하고, Zone의 응답을 클라이언트로
    중계합니다.

  - Zone Server
    존·채널 단위로 게임 로직을 처리합니다. 시작 시 Gateway에 접속해
    자신이 가진 존·채널 목록을 등록합니다.

  - ServerCore (정적 라이브러리)
    두 서버가 공유하는 네트워크 버퍼, DB 스레드 풀, 작업 큐,
    패킷 정의, CSV 로더, 공용 템플릿.

  - BotClient
    부하 테스트용 봇 클라이언트.


--------------------------------------------------------------
3. 주요 구현 내용
--------------------------------------------------------------

[동시성 구조]
  - Zone 하나를 하나의 작업 큐(JobSerializer)로 처리하는 단일 논리
    스레드 구조. 게임 로직 안에서는 락 없이 상태를 관리합니다.
  - DB 작업은 별도 DB 스레드 풀에서 실행하고, 결과는 다시 Zone 작업
    큐로 넘겨 처리합니다. 게임 틱이 DB 응답을 기다리지 않습니다.
  - Gateway의 세션별 송수신은 strand로 직렬화합니다.

[네트워크 / 패킷]
  - 고정 크기 헤더(size, id) 기반 패킷 파싱, 1바이트 정렬 구조체로
    패킷 정의, 가변 길이 목록 패킷(헤더 + 개수 + 배열).
  - 세션 상태 머신(접속 → 로그인 → 로비 → 게임)으로 단계별로 허용된
    패킷만 처리.
  - 송신 큐가 일정 크기(1MB)를 넘는 느린 클라이언트는 연결을 종료해
    서버 메모리 증가를 방지.

[AOI(시야) 처리]
  - 3×3 격자 기반 AOI로 주변 유저에게만 이동·전투·드롭 패킷을 전송.
  - 칸이 바뀔 때만 새로 보이는 칸 / 안 보이게 된 칸의 차이를 계산해
    등장·퇴장 패킷을 전송.
  - 플레이어, 몬스터, 필드 드롭을 각각의 격자로 관리.

[Gateway 멀티캐스트]
  - Zone이 여러 유저에게 같은 패킷을 보낼 때, 대상 세션 목록과
    페이로드를 내부 패킷 하나로 묶어 Gateway에 전달.
  - Gateway는 송신 버퍼 하나를 모든 대상 세션이 공유해 복사와 내부
    통신량을 줄임.

[게임 콘텐츠]
  - 몬스터 AI: 대기 → 추적 → 공격 → 복귀(리쉬 범위) → 사망 → 리스폰.
  - 스킬: 단일 / 시전자 중심 범위 / 대상 중심 범위, 쿨타임, HP·MP 비용,
    스킬 효과 그룹(데미지, 도트, 디버프).
  - 보상: 전체 지급 / 개별 확률 / 가중치 랜덤 방식의 보상 테이블,
    필드 드롭(소유권 유지 시간, 소멸 시간).
  - 인벤토리: 고정 슬롯, 스택, 아이템 추가·제거, 변경 칸만 저장·전송.
  - 레벨·스탯: 누적 경험치 기반 레벨 계산, 직업·레벨별 스탯 적용.
  - 포탈을 통한 존 이동: 이전 존에서 저장 완료 후 다음 존으로 전환.

[기획 데이터(템플릿) 관리]
  - 존, 포탈, 몬스터, 스폰, 보상, 스킬, 스킬 효과, 레벨, 스탯, 캐릭터,
    아이템을 CSV로 관리하고 테이블별 템플릿 클래스로 서버 시작 시
    한 번 로드.
  - 컬럼 이름 기반 접근으로 CSV 컬럼 순서 변경에 영향을 받지 않음.
  - 로드 시 값 범위와 테이블 간 참조(포탈 → 존, 스폰 → 몬스터,
    스킬 → 스킬 효과, 스탯 → 레벨 등)를 검증해 잘못된 데이터로는
    서버가 기동되지 않도록 처리.

[아이템 UID 발급]
  - [초 32비트][서버 번호 8비트][순번 24비트] 구조의 64비트 UID를
    서버가 직접 발급.
  - DB 왕복 없이 아이템을 즉시 생성하면서도, 재시작 후에도 겹치지
    않고 생성 시각·서버를 UID만으로 확인할 수 있어 아이템 복사 추적에
    활용 가능.

[계정 / 저장 / 안정성]
  - libsodium으로 비밀번호 해시 저장 및 검증.
  - 중복 로그인 시 기존 세션 종료 처리.
  - 접속 중인 플레이어를 주기적으로 나눠서 저장(분산 자동 저장),
    변경이 없으면 저장 생략.
  - 서버 종료 신호(Ctrl+C) 수신 시 모든 존의 플레이어를 저장하고
    남은 DB 작업을 모두 처리한 뒤 종료.

[부하 테스트]
  - 로그인 → 캐릭터 생성·선택 → 입장 → 이동·사냥·스킬·부활을 자동으로
    수행하는 봇 클라이언트 개발.
  - 접속 수, 초당 송수신 패킷·바이트, 사망·위치 보정·스킬 실패 횟수를
    주기적으로 출력해 서버 상태를 확인.


--------------------------------------------------------------
4. 프로젝트를 통해 얻은 것
--------------------------------------------------------------
  - Node.js에서는 런타임이 대신 처리하던 스레드, 메모리, 객체 수명
    관리를 직접 설계하며 실시간 서버의 동작 원리를 이해했습니다.
  - 라이브 서비스 운영 경험(데이터 오류, 중복 접속, 저장 누락 등)을
    설계 단계부터 반영하는 습관을 가지게 되었습니다.


--------------------------------------------------------------
5. AI 도구 활용
--------------------------------------------------------------
C++ 학습과 개발 과정에서는 AI 도구(Claude, GitHub Copilot)를 코드
리뷰와 개념 학습에 적극 활용했습니다. 서버 구조와 주요 설계는 직접
결정했고, AI가 제안한 코드는 동작 원리를 검증한 뒤 반영했습니다.
또한 테스트용 데이터 생성, Unity 클라이언트 프로젝트 관리처럼 반복적인
작업에도 AI를 활용해 핵심 서버 개발에 더 많은 시간을 쓸 수 있었습니다.
